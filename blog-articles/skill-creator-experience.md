# 讓 Claude 幫我寫 Skill

## 什麼是 Skill？

Skill 是 Claude 的「可重複使用 SOP」。你把規則、格式、流程寫在一個 `SKILL.md` 檔案裡，之後每次跟 Claude 說觸發詞（例如「幫我寫成文章」），它就會自動照著執行。

就像訓練一個助理：第一次你仔細說清楚怎麼做，之後你只需要說「照老規矩」。不用每次都重新解釋一遍你的標準、喜好和流程。

---

## 為什麼我想做這件事？

我的部落格 `jill425.github.io` 用 Next.js 架設。平常我會有一些技術討論或專案心得，想把它們整理成文章發佈，但每次都要手動做一堆事：

- 想結構（要有幾個 H2？該怎麼組織？）
- 寫 SEO frontmatter（title、description、tags）
- 調整語氣和風格（要不要放代碼片段？要加比喻嗎？）
- 確認沒有廢話或邏輯跳躍
- 實際發佈到部落格

我想把**整套流程包進一個 Skill**，讓 Claude 讀完一段對話就能直接產出可發佈的文章——包括決定結構、寫 frontmatter、確認才發佈，全部自動化。

---

## 怎麼開始？

### Step 1：找到 Skill Creator

在 Claude 的介面，側邊欄可以找到已安裝的 Skills 列表。其中有一個內建工具叫 **Skill Creator**，專門用來幫你設計新的 Skill。

直接跟 Claude 說：

> 「我要建立一個 skill，協助把整個討論串的想法落實寫成技術文章。」

Skill Creator 會開始問你一連串問題，把你的需求一步步轉化成一份完整的 `SKILL.md` 檔案。

### Step 2：回答關鍵問題

Claude 問了這些：

> **目標讀者是誰？語言偏好？長度規範？部落格用什麼框架？發佈流程？**

我的回答：
- **目標讀者**：工程師、技術決策者、以及在招聘或尋找技術資源的 HR
- **語言**：繁中 + 英文技術名詞混搭（不要生硬翻譯）
- **長度**：教學文最多 5000 字，心得文 500–1000 字，重點是別為了填充而寫廢話
- **框架**：Next.js，已在 Cowork 設定好，知道檔案結構
- **發佈流程**：**一定要先確認才能 push 到 GitHub**，防止意外發佈

這些回答直接變成 Skill 裡的規則和檢查清單。

### Step 3：讓 Claude 研究 + 起草

Claude 沒有馬上開始寫，它先去查了熱門技術部落格的文章結構（GitHub Blog、freeCodeCamp 等），再根據研究結果設計出一份完整骨架：

- **四種文章類型**（Tutorial / Deep Dive / Tool Review / Reflection），各有對應章節模板
- **SEO frontmatter 規範**（title 長度、description 要包含什麼、tags 選擇）
- **寫作風格指引**（比喻優先、中英混搭要自然、code block 要有註解）
- **發佈前確認流程**（產出文章預覽，等使用者明確說「確認」才真的 push）

這一步花了最多時間，但值得——清楚的規範意味著未來每次執行都會很穩定。

## 過程中發生什麼？

第一版跑完，文章出來了。看起來有模有樣，但讀起來感覺空洞——每個章節都在「描述接下來要說什麼」，而不是真的在講東西。

```
❌ 原版某段：
## 我想達到什麼目標？
我想把平常的學習對話整理成文章發佈...
```

讀起來就像一個大綱的綱要，沒有實質內容。

---

## 遇到什麼問題？怎麼修？

### 問題 1：文章為了撐結構而湊字數

**根本原因**：Skill 指令方向錯了。它告訴 Claude「要有這些章節」，卻沒有說「先找到最有價值的那個點，再決定章節」。

**修法**：在 Skill 裡加了這條核心原則：

```
一篇文章只講一件事。
從對話中找「最有價值的那個點」，圍繞它寫。
章節要有內容才存在，不要為了結構而湊廢話。
```

這樣 Claude 就會先挑出「最值得說的部分」（比如：遇到什麼問題、怎麼解決），然後只圍繞這個重點寫，多餘的空白段落直接砍掉。

### 問題 2：文章太單調，看不見過程

讀者看不到「我跟 Claude 怎麼互動」、「Code 長什麼樣子」、「UI 的流程是什麼」——全是文字堆砌。

**修法**：在 Skill 裡加了「如何讓文章有畫面感」的指引：

```markdown
1. 嵌入對話片段（blockquote）：
> 我：我想建立一個 skill，把對話整理成技術文章
> Claude：好的，讓我先問幾個問題...

2. 截圖用預留位置標記，發佈前補上

3. Before/After 對比直接並排：
❌ 原版標題：「我們如何一起建立這個 Skill」
✅ 修改後：「讓 Claude 幫我寫 Skill」
```

### 問題 3：標題邏輯不夠銳利

原標題的思路是「描述事件」，但更吸引人的標題是「暗示成果或轉折」。

```
❌「我用 Skill Creator 設計了一個技術文章寫作 Skill」
✅「讓 Claude 幫我寫 Skill」
```

修改後的標題更簡潔，暗示了「你也能這樣做」的行動力。

## 最後產出是什麼？

一份 1200+ 行的 `SKILL.md` 檔案，涵蓋：

✅ **文章類型判斷系統**
- 自動辨識「Tutorial」「Deep Dive」「Tool Review」「Reflection」以及混合類
- 每種類型有對應的章節模板和長度建議

✅ **「有畫面感」寫作指引**
- 對話片段怎麼嵌入
- 截圖預留位置怎麼標記
- Before/After 對比怎麼呈現
- Code block 要加語言標籤和註解

✅ **SEO Frontmatter 自動產出**
- Title / Description / Tags 的邏輯規則
- 什麼樣的 description 既能被搜尋引擎理解，又能吸引讀者點進來

✅ **發佈前確認機制**
- 產生完整的文章預覽
- 列出 Title、Slug、Category、Tags、字數
- 等待使用者明確說「確認」才執行 push

## 我從這個過程學到了什麼？

**1. 設計 Skill 就是系統思考**

你必須把「我想要什麼」拆解成「什麼規則、什麼格式、什麼例外、什麼順序」。說得不清楚，AI 做不出來。所以每一次修改 Skill，其實都是在讓自己的思路更清晰。

**2. Prompt 的「方向」比「詞彙」重要**

「要有這些章節」和「先找最有價值的點，再決定章節」，詞彙量差不多，但執行結果天差地別。方向對了，細節自己會跟上。

**3. 例子和反面例子一樣重要**

在 Skill 裡加上 `❌` 和 `✅` 的對比，比寫 100 字說明都有效。Claude 會自動從例子學習。

**4. 確認機制值得額外設計**

「發佈前確認」這個步驟看起來簡單，但它防止了很多意外。在 Skill 層面設計好，比事後修復重要得多。

## 如果你也想試試

如果你也有重複執行的 AI 工作流（比如「整理會議紀錄」、「生成技術文檔」、「測試用例設計」），很值得用 Skill Creator 試試。

關鍵是：
1. **找到重複的部分**（什麼工作流程你做了很多次）
2. **把規則明確化**（怎麼判斷好壞，什麼是例外）
3. **測試 + 迭代**（第一版往往不完美，根據實際結果修改）

一旦 Skill 成熟了，你就再也不用重新解釋自己的標準和喜好——Claude 會記住，而且每次都一致地執行。
